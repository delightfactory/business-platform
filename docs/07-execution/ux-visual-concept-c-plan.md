# تنفيذ موحد للتحول البصري — Concept C

حالة: معتمد للتنفيذ بطلب المالك المباشر 2026-10-09. الأساس 13b2b7a؛ الفرع ux/visual-concept-c. توجيه المراجع في ux-visual-concept-c-brief.md وخطة Claude المستقلة هما المصدران. عند اختلاف التفاصيل، القرارات التالية تحسم التنفيذ.

## النتيجة المطلوبة
الفرق المرئي وسهولة إكمال المهمة هما القبول؛ إغلاق الورق أو تغيير الألوان وحده لا يكفي. 75 صفحة وكل المكونات والجداول والأزرار الحالية ضمن التحويل؛ لا وظيفة مخفية أو بيانات وهمية لتجميل الشاشات.

## الدمج والقرارات
- Alexandria للعناوين، IBM Plex Sans Arabic للنص، الأرقام 123، رموز وأيقونات Concept C، مظهران وهوية الشركة الحالية.
- إطار علوي للديسكتوب وسفلي للموبايل حسب الدور، خمسة مداخل رئيسية كحد أقصى؛ بقية الروابط في التنقل المحلي والمزيد. لا حذف لأي رابط مصرح به.
- لا inbox جديدة. اليوم يعرض بطاقات المهام بالأعداد الحقيقية وحدود العينة؛ القرارات تبقى في صفحاتها وتستخدم نمط عرض موحدًا.
- HR: الإجازات تحت مجال الوقت؛ روابط الطلبات والأرصدة والإعدادات تبقى واضحة. الموظف: يومي، إجازاتي، ملفي.
- الاستجابة: تحميل على مستوى المجالات، تغذية راجعة فورية، تجميع القراءات المستقلة ومشاركة القراءات المتطابقة داخل الطلب بـReact.cache فقط؛ لا تخزين بين الحسابات/الطلبات ولا تبديل دلالات الخطأ أو الصلاحية.
- إضافة اختيار موقع الحضور من خطة Claude: استخدام موقع الجهاز عند ضغط المستخدم، تعديل نقطة بالخريطة، معاينة النطاق، تأكيد ثم الحفظ عبر action الحالي. الإحداثيات اليدوية بديل. تبقى بيانات الموقع لقناة الحضور الحالية، لا مخطط جديد للفرع.
- Leaflet خفيف للعرض مع بلاطات OSM ونسبة المصدر؛ إضافته مخصصة للخريطة ضمن دمج الخطتين. لا بحث عناوين ولا مفتاح مزود ولا خدمات جديدة. لا اعتماد تلقائي لقيم احتفاظ GPS أو سياسة رفض/مراجعة. القيم الحالية محفوظة، والجديدة يراها المسؤول ويؤكدها صراحة.
- التحول البصري يجري أولًا في الأساس المشترك، ثم إعادة تركيب كل مجال؛ كلاهما مطلوب للإغلاق.

## الدفعات العملية
1. WP0 ثم WP1–4: أساس ثابت، خط/رموز/مكونات ومعرض، إطار وتنقل واستجابة، ربط CSS القديم. مالك واحد للملفات المشتركة.
2. WP5–7: تجربة الموظف واليوم ولوحات القرار، عبر البيانات ومحاولات الاسترداد الحالية.
3. WP8–9: الناس والوقت والإجازات والرواتب والإدارة والمشغّل والدخول، مع الخريطة. مجالات منفصلة بعد إقرار الأساس.
4. WP10–11: تحقق مجمع ومراجعة مستقلة، إصلاح الحرجة/العالية ثم PR إلى فرع الأساس فقط؛ لا main أو نشر.

## التنفيذ الموفر والسلامة
- إعادة استخدام دليل خط الأساس والمرجع غير المتغير، لا إعادة QA قواعد البيانات أو المحاكاة السابقة.
- lint/typecheck/build مجمعة لكل دفعة ذات معنى؛ فحص الملفات المتأثرة أثناء الكتابة؛ لا بناء كامل بعد كل زر أو مكون.
- صور قليلة ممثلة للهاتف والديسكتوب والمظهرين، ومعرض المكونات؛ فحص اللوحي عند اختلاف التركيب. سجلات التشخيص خارج Git، دليل الحزمة README قصير وصور فقط.
- supabase/ وactions المالية/الحضور والعقود والمعاملات والصلاحيات وإيصالات المحاولات وحماية offline تبقى كما هي. لا حسابات مالية أو رصيد إجازة موازية في العميل.
- نماذج الإرسال تحتفظ بقيمها وفروق النتيجة غير المؤكدة/المؤكدة، ولا تظهر نجاحًا وهميًا.
- مراجعة بصرية من المنسق داخل كل دفعة ومراجع مستقل عند التسليم، وفق §5.3 في توجيه المرحلة. حد حساب Claude المعروف لا يوقف التنفيذ المحلي المصرح؛ لا إعادة محاولات على حساب محجوب.
- لا إعادة فتح نطاق خلفي أو دفعات منتهية لأمور غير مؤثرة. الفشل المحدد يُصلح في موضعه، ولا تتكرر حزم كاملة بلا سبب جديد.

توجيه المالك الأحدث: لا إفراط في الأدلة والصور والاختبارات. يكفي build شامل (يتضمن TypeScript) وlint مجمع عند نهاية دفعة مؤثرة، ومراجعة عدد قليل من الصور الممثلة. لا pgTAP لأن الخلفية ثابتة، ولا تصوير كل حالة/صفحة، ولا اختبارات تكرر التنفيذ. يعاد الفحص فقط بسبب تعديل مؤثر أو خطأ محدد. دليل مختصر واحد للدفعة، والمراجعة النهائية تركّز على فرق التصميم والسلاسة.
