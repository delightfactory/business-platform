1. إنشاء مشروع Supabase مستقل للإنتاج، وتسليم رابطه أو Project Ref واسم المؤسسة. حفظ كلمة مرور قاعدة البيانات في مخزن أسرار أو إدخالها مباشرة في الواجهة الخاصة؛ لا توضع في المحادثة أو Git.

3. إتاحة حسابات Supabase وVercel وResend ومزود DNS للمشروع الصحيح، من جلسة موثقة أو اتصال مصرح. عند تعذر الوصول، يتولى المالك تسجيل الدخول أو الموافقة المطلوبة للحساب فقط.

## الخدمات والإعدادات المطلوبة

| الخدمة | إعداد المشروع | دليل الإنجاز المطلوب |
|---|---|---|
| Vercel | مشروع مستقل مرتبط بالمستودع، Node 24، بناء `npm run build`، تحديد فرع الإصدار المقصود | هوية الفريق والمشروع وcommit والنشر الفعلي وHTTPS |
| Supabase Database | المهاجرات الأصلية بالترتيب دون نسخ QA | مطابقة سجل المهاجرات والبصمات وفحص الأمان والصلاحيات |
| Supabase Auth | دخول بالبريد وكلمة المرور، دعوات فقط، منع التسجيل العام والمجهول | مستخدم غير مدعو لا يستطيع إنشاء عضوية؛ نجاح الدخول والخروج والاستعادة |
| Resend SMTP | نطاق إرسال موثق مستقل للمنصة، SPF وDKIM وDMARC مناسبة للنطاق | DNS verified، وإرسال مستلم فعليًا مع سجل تسليم |
| Auth templates | قالبا invite وmagic_link الأصليان في `supabase/templates/`، ومراجعة قالب recovery | رابط يصل إلى المسار الصحيح ويكمل الرحلة، لا مجرد قبول SMTP |
| Supabase Storage | bucket `tenant-branding` خاص؛ حد 2 MiB وصيغ PNG/JPEG/WebP كما في المهاجرة | رفع وعرض الشعار بصلاحية صحيحة ورفض الوصول من شركة أخرى |
| الصيانة | جدولة تنفيذ الوظيفة الحالية `time.purge_expired_channel_location` بهوية موثوقة | تشغيل مسجل وحذف الدليل المنتهي دون حذف سجل الحضور |
| الاسترجاع والمراقبة | نسخ قاعدة البيانات وملفات Storage، سجلات التطبيق/Auth/البريد والمهام | إثبات استرجاع معزول، ومسار واضح لمراجعة فشل البريد أو المهمة |

لا يوجد إعداد Resend API مباشر في التطبيق المفحوص؛ الإرسال الحالي عبر Supabase Auth. لا نضيف مفتاح `RESEND_API_KEY` إلى Vercel لمجرد الربط عبر SMTP، ولا نخلط رسائل الدخول مع حملات تسويقية أو إشعارات غير منفذة في المنتج. أي وظيفة جديدة تظهر ضرورية تُسجل كفجوة محددة قبل تنفيذها.

## متغيرات بيئة التطبيق

| الاسم | مكانه |
|---|---|
| `NEXT_PUBLIC_APP_URL` | عنوان HTTPS النهائي للمنصة |
| `NEXT_PUBLIC_SUPABASE_URL` | API مشروع الإنتاج المحدد |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | المفتاح العام لنفس المشروع |
| `SUPABASE_SECRET_KEY` | خادم Vercel فقط؛ لا يظهر للمتصفح أو السجلات |

لا ننسخ `.env.local` أو `SUPABASE_INTERNAL_URL` من بيئة QA إلى الإنتاج. لا نضع `PLATFORM_OPERATOR_MAINTENANCE_DATABASE_URL` في تطبيق الويب؛ هو اتصال صيانة مؤقت لعملية bootstrap فقط. بيئة Preview تستخدم مشروع اختبار مستقلًا ولا ترث أسرار الإنتاج تلقائيًا.

## ترتيب التنفيذ

### 1. تثبيت الهوية والنسخة

نسجل Project Ref واسم مؤسسة Supabase، وفريق/مشروع Vercel، والنطاق، ومرسل البريد، وcommit الإصدار. نتحقق أن قاعدة البيانات الجديدة تخص هذا المشروع وخالية من بيانات عميل قائم. إذا كانت مستخدمة، نتوقف عن افتراض أنها قاعدة جديدة ونراجع أثر النقل أولًا. نثبت commit نهائيًا قبل التنفيذ؛ تغير المهاجرات يستلزم تحديث manifest.

### 2. بوابة الإصدار وقاعدة البيانات

نشغل lint وtypecheck وbuild على نسخة الإصدار المحددة، مع الاختبارات المرتبطة بالصلاحيات والدعوات والتكامل المطلوب فقط. لا توجد نتيجة CI مسجلة على فرع التطوير وقت التحضير، وworkflow الحالي يعمل على pull_request؛ إعداد مسار الإصدار والتحقق منه جزء من التنفيذ.

نراجع المهاجرات الأصلية لسلامة التنفيذ السحابي ثم نطبقها بترتيبها مع حفظ سجلها، ولا نرفع fixtures أو seed أو محاكاة ضرائب أو حسابات QA. نطابق المهاجرات المنفذة، وواجهات RPC والمنح وRLS وStorage؛ لا نعرض schemas الخاصة عبر Data API. إعداد `supabase/config.toml` المحلي ليس دليلًا على ضبط المشروع المستضاف.

### 3. نطاق التطبيق والبريد

نحدد عنوان التطبيق النهائي، ونضبط DNS وHTTPS. نوثق نطاق إرسال مخصصًا لهذه المنصة في Resend دون تغيير إعدادات Protection Giants. إعداد SMTP حسب الوثائق الحالية: `smtp.resend.com` والمنفذ 465 والمستخدم `resend` وكلمة المرور هي مفتاح Resend؛ تحفظ في إعدادات Auth السرية فقط.

نضبط Site URL على نطاق التطبيق. المسارات التي يستخدمها المصدر:

- `/auth/callback` لاستعادة كلمة المرور.
- `/auth/invitations/callback` لدعوة مسؤول الشركة.
- `/auth/membership-invitations/callback` لدعوات العضوية.
- `/auth/employee-account-activation/callback` لتفعيل حساب الموظف.

المسارات الثلاثة الأخيرة تحمل معاملات سياق في `redirectTo`؛ نسمح بالنطاق النهائي ومساراته المطلوبة ونختبر مطابقة المعاملات فعليًا، دون wildcard يشمل نطاقات Preview عشوائية. نثبت القالبين الأصليين اللذين يضيفان `token_hash` ونوع التحقق إلى RedirectTo؛ لا نستبدلهما بقالب افتراضي يكسر سياق الدعوة. نراجع حدود الإرسال وتكرار الطلب وصلاحية الروابط بدل نسخ الحدود المحلية.

### 4. النشر الأول والتهيئة

نضبط متغيرات الإنتاج الأربعة، ثم ننشر النسخة المحددة ونتحقق من هوية النشر وارتباطه بقاعدة الإنتاج. لا نستخدم بناء QA المحلي السابق لأنه مبني بمتغيرات QA العامة. نختبر صفحة الدخول والدليل وغياب الأخطاء، ونحفظ عنوان النشر وخط الرجوع.

ننشىء حساب المدير المحدد بشكل خاص، ثم نستخدم أداة bootstrap الحالية `scripts/platform-operator-maintenance.mjs` مع UUID المستخدم الحقيقي. الأداة تتطلب اتصال صيانة بدور postgres وتستدعي `platform_private.bootstrap_operator_manager`. لا ننشئ مسارًا عامًا للترقية ولا نعدل المنح يدويًا لتجاوزها. نتحقق من دخول الأوبيريتور، ثم نزيل سر الصيانة من المشغل ونراجع تقييد الوصول المؤقت.

### 5. التشغيل المستمر

نربط تنظيف أدلة الموقع المنتهية بجدولة موثوقة داخل قاعدة البيانات بعد فحص توفر Supabase Cron وصلاحياته. لا تُمنح وظيفة الحذف إلى `authenticated` أو `service_role`؛ المصدر يسحب صلاحياتهما صراحة. نسجل وتيرة التشغيل وحد التأخير المسموح بالحذف ونراجع أول تشغيل. الوظيفة موجودة لكن لا توجد جدولة لها في المهاجرات أو `vercel.json` المفحوصين.

نحدد خطة النسخ المتاحة فعليًا ومدة الاحتفاظ وطريقة استرجاع قاعدة البيانات، ونسخ ملفات Storage بصورة مستقلة؛ نسخ قاعدة البيانات وحدها لا تحفظ محتوى الملفات. نختبر الاسترجاع في وجهة معزولة. رجوع كود Vercel لا يعكس مهاجرات قاعدة البيانات؛ عند فشل مهاجرة نوقف التقدم ونستخدم سجلها وخطة استرجاع/إصلاح محددة دون إعادة عمياء أو reset.

### 6. قبول أول شركة

ننفذ دعوة موجهة فقط لبريد المالك المعتمد أولًا، ونتحقق من التسليم والفتح والتفعيل والدخول واستعادة كلمة المرور. ثم ننشئ أول شركة مقصودة ونختبر تفعيل الخدمة وسحبها، ودعوة المسؤول والعضو وتفعيل الموظف، ورابط منتهي/ملغى، ورفض عبور الصلاحيات بين حسابين وشركتين عند توفر نطاق الاختبار المناسب. الإرسال الفعلي ضمن هذا التحضير يقتصر على البريد الذي يحدده المالك، ولا رسائل جماعية للعملاء.

نختبر الحضور من هاتف فعلي عبر HTTPS قبل الاعتماد التشغيلي عليه، ونغلق رحلة إجازة مناسبة. لا نعلن الرواتب صالحة للاستخدام المالي الحقيقي قبل تأهيل القواعد والمصادر الرسمية والمطابقة المالية المطلوبة. إعداد النشر لا يغير هذه الحدود.

## سجل التسليم المطلوب بعد التنفيذ

هوية الإصدار والمشروعين والنطاق؛ عدد المهاجرات ومطابقتها؛ نجاح الدعوات/الاستعادة؛ هوية المدير دون أسرار؛ نتائج عزل الصلاحيات؛ جدولة الصيانة وأول نتيجة؛ دليل النسخ/الاسترجاع؛ الوظائف المفعلة والحدود المتبقية؛ وخط الرجوع. تبقى كل خطوة غير منفذة معلنة بصفتها كذلك.

تبقى مساحة التطوير في run خارجي عن OneDrive. نحفظ تقريرًا موجزًا والبصمات ونتائج القبول فقط، وننظف المخرجات المؤقتة المملوكة التي لم تعد مطلوبة. لا نزيل قاعدة QA أو النسخ الاحتياطية أو build المستخدم في التجربة الحالية.
