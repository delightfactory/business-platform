## Must-fix: one item, approved + stale + ready

**What happens.** Take a run that is approved and stale, where `approval.ready` is true and the user has `can_lock`.
- `canExecute` is true, so `RunActions` opens with finalize as `primary-button` (`RunActions.tsx:70`).
- `releaseSecondary = canExecute && approved` demotes release (`page.tsx:58`).
- The page's own heading at the same time says "اعتماد يحتاج العودة للمراجعة" (the approval needs to go back to review; `:43`).

So the dominant action points away from what the page itself says to do. This is the approved-state version of the stale + ready contradiction you already handled for review. `staleApproved` reports one default primary, but the fixture doesn't show whether it was ready.

**Fix, choose one:**
- **(a)** Record backend evidence that `approved` + stale reasons + `ready` cannot occur.
- **(b)** Make two presentation-only changes:
  - finalize uses `stale ? 'secondary-button' : 'primary-button'` (`RunActionForm` already receives `stale`);
  - `releaseSecondary={canExecute && work.run.status === 'approved' && work.stale_reasons.length === 0}`.

  Then add an `approvedStaleReady` case with exactly one primary, release. The confirmation checkbox, operation and recovery logic stay untouched. Update the normalization guard so it allows exactly this class predicate.
