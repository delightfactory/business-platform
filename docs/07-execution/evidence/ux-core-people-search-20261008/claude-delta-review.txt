## Must-fix: search box and results can disagree after a reverted edit
**How it happens:**
1. The applied query is "a". The user types "x", and 400ms later the search for "x" is sent.
2. While that request is slow, the user edits the box back to "a".
3. `:23` sees that "a" equals the current query, so it cancels the timer and schedules nothing.
4. The "x" results arrive. Lines 45–46 keep the user's "a" in the box (`ownResult` is true and the text differs from what was sent).

**Result:**
- The box says "a" but the list shows results for "x".
- Nothing is pending, so there's no pending message, and no follow-up search is scheduled.
- The "نتائج البحث عن: x" label partly reveals the mismatch.

This breaks the spec's rule that the latest typed text wins. It's also the kind of misleading-context problem you asked me to reject. The earlier `page === 1` version had the same gap.

**Smallest fix:** in the branch that keeps the user's text (`:46`), if the trimmed box text doesn't match the new `query` and the user isn't composing, schedule the normal 400ms search. Comparing against the in-flight query at `:23` would also work.

Nothing else here is a must-fix.
