# Cube 2 — attendance manual workday slices

Status: first local vertical slice implemented; the remaining Cube 2 Attendance scope is open. Leave belongs to Cube 3.

## Delivered

- `hr.attendance` entitlement and the fixed `attendance.reader.v1`, `attendance.operator.v1`, and `attendance.reviewer.v1` bundles gate the Attendance route and RPCs. Table access remains revoked; SECURITY DEFINER RPCs validate Tenant, entitlement and permission with pinned `search_path`.
- After `hr.attendance` is later disabled, members with Attendance permissions can still read previously materialized history. The UI marks the module disabled and read-only; day opening, event capture, correction and approval remain entitlement-gated.
- An authorized day open materializes at most 50 Work Instances per page, using an employee-code keyset cursor. A candidate is eligible only when its operational date has begun in that Work Policy version's IANA timezone. Cairo is the UI's default date only; it is not a global server-side cutoff. Opening a day pins Employment, Assignment, policy version and timezone/expected instants. Later People/policy changes do not reinterpret an existing instance.
- Fixed overnight shifts remain one operational day. Local timestamps that are ambiguous or nonexistent under timezone rules fail closed for review rather than being guessed.
- Manual IN/OUT entries are append-only and idempotent by request key and payload. A reviewer with `attendance.correct` can append a missing event only on a review/approved record and must provide a reason; it has a distinct audit event. A manager also must provide a reason when appending to any non-open record. The legacy five-argument entry RPCs are revoked from `authenticated`; the six-argument local-time RPC is the only user-callable append path. Corrections preserve original evidence and require a reason.
- The database rejects manually entered or corrected event instants more than five minutes ahead of server time. A previously approved fact cannot be approved again from the same unchanged interpretation; the UI exposes reapproval only after a newer interpretation.
- Fixed-shift Work Instances freeze the policy's scheduled break and V1 five-minute lateness/early-leave grace defaults. A complete IN/OUT pair produces gross elapsed minutes, net minutes after the scheduled break, late minutes beyond grace, and early-leave minutes beyond grace. The UI labels the break as scheduled; it is not separately observed break evidence.
- Flexible Work Instances freeze the required duration and the configured/default local punch window. They do not invent an expected start or lateness metric. A complete pair reports actual net duration; if it falls below the required duration, the result is reviewable and approval requires a reason. Flexible Work Policies are already creatable and assignable through the existing policy editor and employee task.
- An Attendance policy manager can save a dated policy override for one Employment and a specific day or inclusive range of up to 90 days, without changing the People work assignment. The RPC freezes the current policy version, requires the active Employment to have same-Tenant active Site assignments across the dates, and prevents overlapping overrides. Opening a day selects the override policy and freezes its version on the Work Instance. Any date already materialized is rejected; future overrides can be cancelled with a reason before their policy-local effective date. The employee detail page shows the bounded override history and forms.
- An Attendance operator can import up to 100 UTF-8 CSV events (256 KB) after mapping five source columns and reviewing a row preview. Employee code and a unique active same-Tenant Site name must match the effective Assignment; the timestamp must include an explicit offset and fall inside the applicable frozen policy window. The import RPC revalidates each selected row and isolates row failures, so accepted rows commit while rejected rows remain visible. A stable source event key makes an identical reimport idempotent and rejects a conflicting payload. Imported events use the canonical manual-punch evidence and existing Work Instance interpreter/correction path; detail shows that an event was imported and its source key. File row numbers remain display hints and are not persisted as trusted audit provenance.
- Interpretation produces a bounded `ready` or owned `needs_review` result. A fully elapsed shift with no evidence becomes an `absence_candidate`; a reviewer with `attendance.approve` can record a reason and approve a versioned one-day nonfinancial absence fact. A partial punch remains a missing-punch review. Ordinary approval also produces an immutable, versioned nonfinancial fact. Later evidence/correction marks the instance for review; reapproval preserves the prior fact and links the new version to it.
- Work Policy versions can explicitly enable overtime candidates and freeze a minimum raw threshold and round-down increment on each Work Instance. A fixed shift measures only time after its frozen scheduled end; a flexible day measures net duration above its frozen required minutes. An eligible quantity is created only after the related attendance fact is approved. Reviewers with `attendance.approve` must approve or reject with a reason; decisions and superseded candidates remain append-only and audited. A later attendance fact supersedes any undecided candidate from an older fact.
- The review queue at `/tenant/[tenantId]/attendance/review` shows bounded date-based exception, clean-ready, and pending-overtime views with counts, owner labels, and employee-code keyset paging. Reviewers can select up to 50 clean ready days for one bulk approval action. The RPC locks and revalidates every row through the existing single-day approval path; stale, missing, or exceptional rows are skipped individually, with per-item and batch audit events plus explicit partial results. Ambiguous, missing, absence, short-workday, and overtime decisions remain individual tasks requiring their existing review/reason path; there is no bulk exception decision.
- `attendance_payroll_input_projection` returns a read-only v1 projection for a date range of at most 31 days, paged at up to 100 rows. It includes only Work Instances still approved and their latest approved Attendance fact, with source IDs, policy version, correction pointer/reason, and a stable per-input version token suitable for consumer deduplication by Work Instance plus `input_version`. The projection is a live read, not a persisted or cross-page atomic snapshot. It carries only nonfinancial work/late/absence quantities and approved overtime quantities attached to that same current fact; pending, rejected, superseded, or newly stale inputs are excluded. It explicitly returns `boundary_status: projection_only` and `consumed: false`. It requires an active Tenant Attendance permission but deliberately does not require the Attendance entitlement, so authorized historic input remains readable after entitlement loss. No Payroll publication ledger or consumer exists in this slice.

## Deliberate V1 boundary

This slice supports fixed/flexible schedules, dated policy overrides, manual events, bounded CSV import, ordinary overtime quantity review, safe bulk approval of only clean ready attendance days, and a read-only projection contract. Grace defaults are currently five minutes and are not configurable in the policy editor. Overtime is disabled by default per policy. This release records the `ordinary` category only; it has no approved day/night boundary, weekly-rest classification, or official holiday calendar, so it does not infer those categories. Overtime decisions and projected quantities are nonfinancial; the projection is not consumed by Payroll. Leave, device ingestion, monetary absence/late valuation, bulk exception/overtime decisions, and scheduled Work Instance creation remain out of scope. Before any Payroll consumer is enabled, one transaction must lock the affected Payroll run/period, compare each input's `input_version` with its consumed source, and route a changed source that was already consumed by a locked run to an explicit linked correction or next-period adjustment requirement. The prior consumed ledger must remain immutable; do not silently consume the changed projection or reopen a locked run. This gate is not implemented, and no dummy Payroll-lock table is present.
