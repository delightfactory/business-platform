## 1. تشخيص فشل وسيلة الحضور

قاعدة البيانات تفرض وسيلة هاتف واحدة لكل فرع بواسطة `channel_mobile_site_idx` على `(tenant_id,site_id)` عندما `kind='mobile'`. تحققنا من الفهرس الفعلي في الإنتاج، ومن وجود وسيلة هاتف واحدة للمقر الرئيسي في Delight. الوسيلة الموقوفة أيضًا تشغل الفرع؛ التفعيل محفوظ في إصدار مستقل ولا يدخل في شرط الفهرس.

واجهة الإنشاء تعرض الفرع نفسه وتسمح بإكمال النموذج دون بيان أنه مجهّز بالفعل. أُعيد الاختبار محليًا باسم صحيح، وفرع لديه وسيلة هاتف، واختيارات وقيم صحيحة؛ انتهى الحفظ إلى الرسالة العامة اللبني. إذًا هذه حالة فشل مثبتة تتطابق مع وصف المستخدم، والسبب المرجح لمحاولته، وليست فرضية عن حقل ناقص.

المفترض أن تكون المهمة «إعداد حضور الهاتف لهذا الفرع»: إن وُجد إعداد يُفتح لإدارته، وإن لم يوجد يبدأ إنشاؤه. لا يتطلب تعديل سياسة الفرع إنشاء وسيلة ثانية. تغيير الاسم أو إعادة المحاولة أو إيقاف الوسيلة القديمة لن يزيل قيد الفرع، وحذفها لتجاوز القيد يضر بالسجل.

هناك عيب إضافي مؤكد: اسم من حرف واحد يمر من المتصفح لأن `minLength` غير محدد، ثم ترفضه قاعدة البيانات التي تشترط حرفين بعد إزالة الفراغات. النتيجة العامة نفسها لا تعرّف المستخدم بالخطأ. أُعيدت هذه الحالة منفصلة؛ لا نفترض أنها سبب محاولة المستخدم.

**السبب التقني لغموض النتيجة:** `MutationForm` يعرض دائمًا `tone="info" role="status"` للانتظار والنجاح والفشل، و`mutateChannel` يحوّل معظم الأخطاء المعروفة إلى «تحقق من الحقول والفترة والموقع»؛ نموذج الوسيلة لا يحتوي أصلًا على فترة. يحتفظ النموذج بالقيم، وهي خاصية سليمة يجب الحفاظ عليها.

## 3. خريطة الرحلات الحالية

**الحضور:** الوقت ← وسائل التسجيل ← إضافة ← الاسم والنوع والفرع والتفعيل ← الموقع والخصوصية وضبطGPS ← السبب ← الحفظ. عند وجود وسيلة هاتف للفرع لا يتاح مسار حل واضح من الرفض. جاهزية الموظف تتطلب كذلك العمل والفرع والقالب والحساب والصلاحيات.

**الإجازات:** الوقت ← إعدادات الإجازات ← اختيار الجهة ← مركز الإعداد ← التقويم ثم العودة ← السنة ثم العودة ← النوع ثم العودة ← الأرصدة ← البحث عن الموظف ← نوع الحركة ← الفترة ← النوع ← الأيام والحفظ. مركز الإعداد يوجّه للخطوة التالية بالفعل؛ لا نحتاج استبداله تلقائيًا بمعالج شامل أو فرض معالج على التعديل المتكرر.

**الرواتب:** مساحة الرواتب ← إعداد مواعيد الجهة ← رابط إعداد البنود والسياسة ← صفحة المدخلات في وضع الإعداد وفترة مختارة ضمنيًا عند غياب الفترة. يوجد سياق مهم للجهة والفترة والإصدارات؛ المطلوب عرضه بصورة مفهومة مع تحديد ما يخص الشركة وما يخص الفترة.

## 4. الرحلات المقترحة

### مدخل وتنقل متسقان

يبقى الهيكل العام «الناس / الوقت / الرواتب» ويُراجع تجميع التبويبات ومواقعها داخل كل مجال. تتقدم مهام التشغيل اليومية، ويظهر إعداد المجال كتجميع واضح ثابت. لا نضيف مجال إدارة عام جديدًا أو نخفي روابط مصرحًا بها لمجرد تقليل عددها. الروابط القديمة والمباشرة واستعادة السياق والصلاحيات تبقى مدعومة.

خريطة جاهزية على مستوى المهمة تربط الإعدادات ذات الصلة: «ما المطلوب ليتمكن موظفو هذا الفرع من الحضور؟» و«ما المتبقي لإتاحة طلب الإجازة؟». حالاتها تُشتق من قراءة موثوقة ومصرح بها: مكتمل، يحتاج إجراء، تعذر التحقق، أو يتطلب مسؤولًا آخر. لا يتحول «لم نقرأ البيانات» إلى أخضر مكتمل أو فراغ.

### أ. إعداد حضور الهاتف للفرع

1. اختيار الفرع وطريقة التسجيل، مع عرض الفرع الوحيد المؤكد دون إعادة اختياره.
2. التحقق من وجود وسيلة الهاتف لهذا الفرع: إما إدارة الموجودة وحالتها الحالية، أو إكمال الإنشاء. المصدر الخارجي يحتفظ برحلته المستقلة وتعدد المصادر وربط الموظفين.
3. قرار الموقع والخصوصية: الخريطة والمسافة، ومدة الحفظ بقيمة ووحدة مفهومة؛ تُحوّل إلى الثواني الصحيحة نفسها التي يقبلها الخادم. لا قيم افتراضية لسياسة الخصوصية أو رفض التسجيل.
4. ضبط الدقة وهامش السماح وعمر القياس في مجموعة مساعدة متدرجة. إن كانت قيمًا مطلوبة وغير مكتملة، تظهر الحاجة إليها قبل التأكيد وتُفتح مجموعتها عند الخطأ؛ لا تختبئ متطلبات الحفظ.
5. ملخص قابل للمراجعة يوضح الفرع والنطاق والحفظ ونتيجة فشل التحقق وبدء الاستقبال أو حفظه موقوفًا. السبب يبقى وفق العقد الحالي. الاسم والنوع والفرع للوسيلة القائمة ثابتة، والإعدادات الجديدة إصدار محفوظ.
6. نتيجة محفوظة صريحة، مع الإجراء التالي الفعلي. عند تعارض متزامن نوجّه للموجودة؛ وعند نتيجة شبكة غير مؤكدة نتحقق قبل إعادة الإنشاء.

التحقق الاستباقي يحتاج قراءة معتمدة تعيد وجود الوسيلة وحالتها للفرع، عبر عقد قائم ملائم أو تعديل محدد لعقد القراءة. أول20نتيجة ليست دليلًا على عدم وجودها. تبقى الصلاحيات والقيد الفريد وقفل المعاملة سلطة الحفظ النهائية؛ لا تحديث أو تفعيل تلقائي للموجودة.

### ب. أول إعداد للإجازات ثم الإدارة المعتادة

اختيار الجهة مرة واحدة ← مركز تقدم واضح: تقويم، سنة رصيد، أنواع، أرصدة عند الحاجة ← حفظ كل جزء والعودة للخطوة التالية بسياقه ← مراجعة موظف من داخل سياقه. تعديل نوع أو تقويم قائم يبقى مباشرًا. الأرصدة لا تُنشأ تلقائيًا ولا نستنتج استحقاقًا من تاريخ التعيين. عدم فحص أرصدة الموظفين يظهر بهذه الصفة، ولا يُعرض كحاجة مؤكدة لإضافة أرصدة أخرى.

### ج. إعداد الرواتب ثم تجهيز الفترة

فصل مفهوم «تهيئة مواعيد وبنود وسياسة الجهة» عن «تجهيز ومراجعة فترة معينة»، مع مدخل إعداد متسق وروابط تربط المرحلتين. تُراجع تبعية كل إعداد في العقد الفعلي قبل إزالة اختيار فترة أو تغييره. تاريخ التطبيق واضح، والجهة والفترة الحالية مثبتتان؛ إذا لم يُحدد سياق صالح يُعرض الاختيار أو أساس الاقتراح صراحة. لا نغيّر تلقائيًا قاعدة الفترة إلى «اليوم» قبل مراجعة الفترات الانتقالية والعقود.

تتقدم المهمة المطلوبة الآن على أرشيف الفترات. التاريخ والإصدارات متاحان عند الطلب؛ حواجز المسير المفتوح والحضور والتاريخ المقفل والاعتماد تبقى محفوظة.

## 5. ترتيب التنفيذ وضوابطه

**P0 — إصلاح الرسالة ومسار التعارض:** ترجمة تعارض الإنشاء المعروف الذي يخص `channel_mobile_site_idx` إلى وجود وسيلة هاتف للفرع، ورابط لوسائل التسجيل. تمييز النتيجة الصحيحة بصريًا ودلاليًا، ومطابقة قيود الاسم والسبب بعد إزالة الفراغات. إبقاء الأخطاء غير المعروفة غير مشخصة تخمينيًا، وإبقاء تحذير عدم تأكد النتيجة والتحقق قبل التكرار. هذه إصلاحات محددة لا تستلزم إزالة القيد أو تغييرSQL.

**P1 — مواصفة التنقل والجاهزية:** خريطة مداخل وتبويبات حسب الدور والحالة؛ كل قدرة حالية لها مكان واضح. تحديد عقود قراءة الجاهزية والوسيلة الموجودة، والصلاحية والتعثر والنتيجة غير المؤكدة. قياس خط أساس قبل إعادة ترتيب التنفيذ.

**P2 — حضور وإجازات:** بناء الرحلات المقترحة، ثم تجربة الإعداد الأول والإدارة المتكررة والحالات السلبية. لا معالج موحد لكل النماذج ولا توسع معماري غير مطلوب.

**P3 — الرواتب:** بعد حسم نطاق الشركة والفترة وتواريخ التطبيق، تنفيذ شريحة إعداد ومراجعتها مع الحالات الانتقالية والمقفلة الموجودة. لا تعديل حسابات الرواتب أو منح صلاحيات لتجميل الرحلة.

تُسجل قرارات السلوك وعقود القراءة اللازمة في المواصفات ومراجعةissue47 قبل تغييرها. الاسم المقترح أو نمط التفعيل أو قيمGPS ليست افتراضات تنفيذية صامتة. لا نخفف أسباب التدقيق أو خصوصية الموقع أو شروط الرصيد والاعتماد. تُحدّث تعليمات الاستخدام مع الرحلة النهائية، وتُجرى الفحوص المناسبة للحزمة مرة واحدة؛ لا إعادة اختبارات قاعدة بيانات أو بناء شامل بعد كل مكون.

## 7. المراجعة والأدلة

مراجعة Codex تتفق مع الأولويات أعلاه، وتصحح التوسع في فرضية ضرورة معالج شامل للإجازات. مراجعة Claude الرسمية `24e6a909-33c3-43d9-8f66-9cde3f4e67b2` قرأت المصدر والصور في جولتين محددتين: دراسة عامة، ثم ملحق اكتشاف تعارض الوسيلة. لا تعديلات من المراجع، و`readOnlyViolation=false`. التقرير وملحقه محفوظان هنا منفصلين. أحكام التحليل ليست قبولًا بصريًا أو موافقة مستخدم على إعادة التصميم.

الأدلة المختارة في `images/`: نموذجGPS، فشل التكرار بقيم صحيحة محليًا، إعداد مواعيد الرواتب وإعداد بنود الشركة محليًا، ومدخل ومركز إعداد الإجازات في الإنتاج. الملفات الخام ونتائج التشخيص خارجOneDrive في المسار المملوك `settings-ux-audit-20261016`. لا تبعيات أو خوادم مؤقتة جديدة ولا تغييرات في بيانات الإنتاج؛ الأدلة التشخيصية تُحفظ إلى أن تُغلق المعالجة، ولا ندعي تنظيفًا أو استرداد مساحة من هذه الدراسة.
