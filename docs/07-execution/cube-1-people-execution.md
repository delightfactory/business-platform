## Outcome and slices

Deliver complete, usable People journeys in bounded slices: (1) employee onboarding and directory with authoritative access; (2) organization context and assignment changes; (3) effective compensation and employment lifecycle; (4) optional employee/user linking; (5) named Time work-policy context where Attendance is enabled; (6) workforce import with preview, confirmation and reject report. Each slice closes its UI, database, permission, failure, audit and focused test path before the next one.

## Work assignment transfer and history — implementation slice, 2026-09-30

Employee detail now shows a bounded history of the latest 100 work assignments and a focused transfer form for users with `org_context.manage`. Older records are retained but not pageable in this UI yet. Read history uses `people.view`; transfer choices and schedule/cancel RPCs enforce `org_context.manage`. Site, Department, Job and optional manager are validated in the authoritative transaction for Tenant, active status, Employment Employer, Job/Department match and manager self-reference. A manager must be a same-Tenant active Employee whose Employment is active by the assignment's effective date; reporting remains a simple assignment reference, not an org graph. Transfer option lists are capped at 1000 choices each and report truncation to the UI.

Transfers may start today or later. `valid_until` is exclusive, so the prior interval ends exactly on the new assignment's effective date. The exclusion constraint remains the overlap guard. Cancel is available only before a future assignment takes effect; it removes that future row, restores the prior interval and records both contexts in an append-only actor/Tenant audit event. A change effective today is already active and cannot be cancelled through the future-transfer action. The current V1 limit is one pending future assignment per Employment; HR must cancel it before scheduling another. Backdated transfers and effective dates not later than the current assignment's own start are rejected. Finalized downstream context is outside this mutation path. The physical-device gate remains deferred for this People workflow.

An audited `تصحيح بيانات العمل اليوم` action handles an initial assignment created on the Employment start date: only that day's open initial row can be corrected, its assignment ID is preserved, and site/department/job/manager are revalidated. Future-start managers are shown with their start date and accepted only when active by the transfer effective date; a manager who starts after that date is rejected. This correction is a Cube 1 boundary while Attendance/Payroll consumers are absent. Cube 2 and Payroll must block this correction once downstream facts consume the work context, and must preserve the context consumed by finalized facts.

## Base compensation change and history — implementation slice, 2026-09-30

Employee detail now reads a bounded effective-dated base-compensation history using `compensation.view` and exposes change/cancel actions only under `compensation.manage`. The amount stays EGP with exact two-decimal numeric semantics; the Employment pay basis determines whether the label is monthly or daily. A normal change closes the prior version at the new `valid_from` date (exclusive end) and inserts a new version. A bounded backdate may split only the currently effective open version at a date strictly after its `valid_from`; the prior amount and version ID stay unchanged. A backdate into an earlier, already superseded interval is rejected. On the Employment start date, an initial same-day amount correction is allowed only while the initial row is the sole version; it preserves the version ID and writes before/after audit. One pending future version is allowed per Employment; HR must cancel it before selecting a different amount/date. Cancelling a future version removes only that not-yet-effective row, reopens the preceding interval, and retains the removed amount and restored context in audit. Values already effective cannot be canceled. The physical interval invariant (`valid_until > valid_from`) prohibits zero-length versions; same-day initial corrections therefore use the explicit audited exception instead of creating another same-date row.

There is no Payroll run/lock integration in Cube 1, and this slice does not claim locked-period detection or create a placeholder lock table. The People UI flags that Payroll lock checking is not connected when a past effective date is selected. Before Payroll consumes these versions, the compensation mutation must invoke a server-side Payroll guard in the same transaction, keyed by Tenant, Employment, affected `compensation_versions.id`, proposed effective date and proposed amount. Payroll must inspect locked runs whose periods overlap the proposed changed range and whose consumed input references the affected version. With no affected locked run, the effective change may proceed and any calculated but unlocked run must become stale/recalculation-required. If an unpaid locked run consumed the version, persist a linked correction requirement and route it through the immutable Amendment Run flow; if any payment was recorded, retain the original payable/ledger and route a linked adjustment to the next open period or an approved external settlement. Never edit a locked run or silently apply a retroactive version. The stable Payroll input contract is the version ID plus a snapshot of amount/currency and the covered period; correction records must link the affected version and run(s), preserve the proposed effective change and reconcile the resulting amount. Until this guard exists, backdates are limited to splitting the currently effective version and are not Payroll-lock aware.

## Employment termination and rehire — implementation slice, 2026-09-30

Employee detail supports ending an already-started active Employment and rehiring an ended Employee. Termination requires `people.manage`, `employment.manage`, `org_context.manage`, and `compensation.manage`; rehire uses the same gates because it creates Employment, assignment, and initial compensation together. The Employee identity and code remain unchanged. Rehire creates a distinct Employment after the prior inclusive end date, with a new assignment and base-pay version. Tenant membership is not readjusted or revoked.

A future-start rehire is projected as `scheduled` in both the employee snapshot and directory. Its planned initial Site/Department/Job is shown in the detail summary against the new Employment start date, while the work-context history labels that row as the initial scheduled context rather than a transfer. The initial assignment cannot be cancelled through the transfer RPC because no preceding interval exists to restore. Initial compensation is labeled “pay at work start” and is excluded from pending-change blockers and cancellation actions.

Termination accepts today or a bounded past date, never a future date in this V1. The underlying Employment constraint requires active rows to have a null end date and ended rows to have an end date; the schema has no scheduled-end status transition or finalizer, so storing a future date as ended would end the Employee too early, while retaining active status would leave a stale active Employment after that date. A past date is allowed only if no assignment or compensation version became effective after that date through today; crossing a later effective change is rejected rather than deleting or rewriting effective history. The ending context closes at the day after the inclusive final work date (exclusive interval boundary). Not-yet-effective future assignment and compensation changes are removed transactionally, with the canceled values preserved in their respective audit streams.

The append-only private Employment lifecycle stream records actor, before/after Employment and Employee state, context IDs, canceled pending rows, and the required Payroll final-settlement, Leave balance, and Employee Finance balance handoffs. The Arabic detail flow requires HR to acknowledge that those domains are not connected. It does not claim that settlement or leave/finance review occurred. A backdated termination may affect an already-consumed Payroll period; no Payroll lock check or correction request is implemented here. Before Payroll consumes these records, the termination RPC must call a same-transaction Payroll guard keyed by Tenant, Employment, inclusive end date and affected assignment/compensation version IDs. Unlocked calculations must be invalidated; locked unpaid runs need an immutable Amendment Run requirement; paid runs need a linked next-open-period or approved external adjustment. A later scheduled-end capability must add an explicit pending state and a reliable effective-date finalizer before accepting future end dates.

## Workforce CSV import — implementation slice, 2026-09-30

The People directory now links to a focused import flow gated by `people.manage`, `employment.manage`, `compensation.view`, `compensation.manage`, `workforce_import.execute`, and the active `hr.people` entitlement. Downloadable UTF-8 CSV template uses a fixed ordered header for Employee code/name, Employer/Site names, Employment start, pay basis/amount/eligibility, Department code and Job code. The server parser accepts BOM, quoted commas/newlines and escaped quotes; it rejects malformed quoting/header/column shapes, formula-like cell values, files above 256 KiB, and files above 100 data rows. Physical CSV record start lines are preserved across blank and quoted multiline rows for preview and reject-report display; this line number is a client hint, not authoritative audit provenance, and is omitted from the database audit event. Unknown catalog creation is not offered in V1; unknown, inactive, ambiguous, cross-Tenant or mismatched Employer/Site/Department/Job references are rejected with Arabic row reasons. A single active Employer/Site can be selected as a safe default, but the row is visibly marked as a warning and unchecked until the operator selects it.

Preview validates every row without writes, reports ready/warning/rejected counts, and permits selecting only importable rows. Rejected rows are never passed to confirmation and can be downloaded as a formula-safe CSV report. One tenant-scoped confirmation RPC takes the same advisory locks used by catalog/entitlement changes, revalidates all selected rows, then inserts Employee, Employment, initial Assignment, EGP base Compensation and one `employee.onboarded` actor audit event per employee inside a single transaction. Any stale/invalid selected row returns refreshed reasons with zero rows committed; uniqueness/FK/check races roll back the entire selected batch. No direct table grants or per-row RPC loop were added.

## Optional Employee ↔ Tenant User link — implementation slice, 2026-09-30

Employee detail shows whether an optional account link exists to users with `people.view`; the linked email/name and identity are visible only to `people.manage` or `tenant.members.manage`. Linking choices and link/unlink actions require `people.manage`. The choices RPC returns a bounded searchable page of up to 50 same-Tenant active Memberships whose Auth identity has a confirmed email and is not deleted or currently banned. The mutation RPC repeats those checks authoritatively. A Tenant User can be linked to only one Employee and an Employee can have only one active link in that Tenant. Employees whose workforce status is ended remain linkable because Employee identity is retained; linking does not depend on or alter Membership state, roles or permissions. Unlinking soft-closes the episode, retains its record and appends an actor/Tenant audit event; it does not delete Employee/User or deactivate Membership.

When no suitable account exists, Employee detail keeps the ordinary Tenant invitation path and adds a separate direct account path available only when the operator has both `people.manage` and `tenant.members.manage`; the controls are independently gated. Direct provisioning records a durable, request-keyed intent before calling Auth. The server creates an unconfirmed user without a password and attaches a server-generated intent marker; after the Auth response, an authorized recovery RPC captures only the matching Auth ID/email/intent/random marker (the Auth insert trigger also captures when those values are present at insert). Existing same-email identities are never adopted and leave a durable manual-review state. The server sends an Auth Admin invite email to the marked account, which works while ordinary public signups are disabled. The recipient verifies the email and sets their own password, then an authoritative RPC rechecks that the issuer still has both required permissions and creates only the empty-permission `tenant.member.v1` Membership and Employee link atomically. Capacity is checked under the shared Tenant membership lock at activation; a full Tenant leaves the operation recoverable for recipient retry. HR can retry delivery for recoverable operations. Provisioning intents and append-only actor audit remain private. No automatic Membership revocation is coupled to ending Employment.

## Named Work Policy / Shift template foundation — implementation slice, 2026-09-30

The commercial entitlement catalog now includes independent `hr.attendance`; it is not a prerequisite for `hr.people` or `hr.payroll`, so employee onboarding and compensation remain usable when Attendance is disabled. The Operator entitlements UI can enable/deny it. Time-owned `time.work_policy_templates` and immutable `time.work_policy_versions` provide fixed-time or flexible-duration named templates with bounded local-time, workday, timezone, break, and attribution fields. Arbitrary rule scripting, lateness/overtime interpretation, attendance capture, and leave behavior remain outside this slice. `attendance_policy.manage` is a distinct fixed role bundle; it does not reuse `org_context.manage`. Policy activation/deactivation applies only to future selection and leaves assigned version snapshots intact.

People stores optional `(template_id, version)` on effective-dated work assignment rows. Employee detail shows the policy reference history and allows an `org_context.manage` user to schedule an active named policy from today forward, preserving Site/Department/Job/Manager and closing the prior interval at the new date. The attendance entitlement must be active; the assignment is optional and does not gate onboarding. The policy reference is a tenant-composite FK, template options omit inactive templates, and actor/action audit records cover template versions, status changes, assignments and future-assignment cancellation. Time policy catalog administration uses `attendance_policy.manage` plus `hr.attendance`; permission-gated pages expose templates without granting People access.

The Time module remains the authority for applying policy versions to Work Instances and attendance facts. Before Payroll consumes interpreted facts or work-context snapshots, Cube 2/Payroll must add same-transaction lock/correction guards; this slice does not claim any Attendance or Payroll calculations or downstream lock integration. Physical device and assistive-technology gates remain deferred.
