# Employee rewards and penalties

Owner request: employee profile is the daily entry to add, approve and see monetary rewards/penalties; approved entries feed the appropriate payroll run without re-entry. This is a scoped journey change, not a disciplinary case-management module or automatic payment.

Actor: company manager or delegated finance author/approver who also has access to the employee profile. Existing employee_finance.manage/approve/view and payroll_config.manage remain independent. No new roles or grants.

Entry: Employees > employee > المكافآت والجزاءات. Derive employer and current employment from the authoritative employee snapshot. Default only a uniquely matching current Cairo period; require an explicit choice otherwise, retain older-period paging and allow exact scoped period links. The user chooses reward/penalty, amount and reason. Component choice appears only when multiple eligible company types exist. Reference is optional with truthful internal provenance; a penalty uses employer_penalty classification. Existing saved deduction classification and consent evidence are preserved.

End: save draft > redirect to focused saved record > review > explicit approve > authoritative approved status. No save-and-approve privilege conflation. Existing calculation consumes the approved period adjustment once under the original engine. A calculation made before an input changes must be recalculated. Approval does not pay money or rewrite a finalized payroll. Cancellation stays available before frozen history. Existing governed correction is linked for authorized historical work.

First-use setup stays in the employee context for missing reward/penalty types. Only payroll_config.manage may create a company type, using the original component command. The company explicitly chooses tax/social treatment; the interface does not invent a default financial treatment. No permission elevation. Automatically generated type keys retain duplicate protection without preventing setup when an older type is inactive. Existing records retain their saved type and exact reference shape; unavailable types are flagged for review instead of silently substituted.

Read API: employee-scoped projection, private tables stay private; profile and finance authorization required; exact tenant/employer/employment/period matching; 24 period choices, 20 displayed records plus lookahead, 101 component choices plus honest overflow continuation, and an independently scoped focused record. No other employee records reach the browser. New read function does not alter any existing write engine.

Recovery: unavailable/denied projection explains retry or required role; invalid scope is rejected; no suitable period links to preparing payroll; payroll-ineligible employment explains the Salary section; disabled service allows historical reading only; frozen period displays history and directs to an open period/correction. Validation retains entered values. Draft edits must be saved before approval/cancellation. Existing input CAS, receipt, source validation, entitlement, locking, audit and frozen-history guards remain authoritative. Browser transport interruption limitations of the reused input command must be assessed during qualification; no automatic retry is introduced.

Before/after comparison: previous route starts in payroll inputs and requires employer/period/employee context; the new employee entry fixes employer/employee and defaults the unique current period. These are source-observed decision differences, not measured runtime navigation/time savings. Acceptance requires actual rendered save/approve and calculation inclusion plus key denied/cross-scope/stale/frozen cases. No numerical improvement claim until measured.
