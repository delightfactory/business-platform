## Job, authority and shortest safe journey

An invited admin creates the invited company; a member joins the invited company; an employee activates only the linked account. Entry is the original recipient link. Verify the current issuance/intent and invited identity, set a password only when needed, confirm the existing operation, then enter the server-authorized workspace. Do not ask for company/role selection already fixed by the invitation. Permissions and business authority remain in current validation/actions/RPC/layouts; no role is inferred from the demo, email text or query string.

Each state has one clear next action, truthful feedback and retained safe reference/context. Never retain/repopulate passwords, token hashes or credentials. Session/expired/stale/unknown results need separate recovery explanations; no automatic or blind mutation retry. A marker failure after provider update must explain the partial outcome rather than imply the password definitely failed. UI success requires authoritative record/readiness, not a redirect state. Metrics N/C/P/I/B remain unmeasured for these action journeys; do not turn source links into click counts.

## Corrections to the preserved Claude contribution

1. `removeProvisioningMarker` does **not** fail silently on every path: missing prerequisites return and returned update errors are ignored, but thrown SDK failures are uncaught and can interrupt the redirect. Same distinction applies to defer: returned errors are ignored; thrown errors escape. Record returned-error and thrown-error partitions separately.
2. `state=activated` is a URL redirect value, not necessarily a displayed success. Current employee page independently checks snapshot.state and password_ready, as fixed by R2-ENTRY-01. Do not undo that authority or conflate marker cleanup with account activation.
3. Existing read sources are present: admin/member acceptance pages call validate RPCs; employee page calls activation snapshot. These are not automatically sufficient to resolve a previously committed unknown mutation, and source-only review does not prove they are read-only or expose every terminal result. Review actual SQL/record contracts before using them as reconciliation APIs.
4. Existing signOutAction and forms are present on admin/member accepted-page headers and admin status pages. Missing/limited identity recovery must be assessed per actual page; there is no platform-wide missing-signout finding.
5. `issuer-lost` is loss of issuer authority, not proof the invitation was revoked. Suspended tenant, invalid target, stale issuance, expiry and revocation stay distinct unless authoritative contracts prove otherwise.
6. Tenant-unavailable/link-conflict/membership-conflict map to retry today. This is a source fact and a recovery-design risk, not proof retry cannot ever succeed after an administrator resolves the cause.
7. No new readiness-only privileged action is authorized or specified by this source review. Do not add one merely to avoid re-entry; first establish eligible recipient/session, current issuance, audited authority, consistency/idempotency and recovery contract.
8. Provider error/exception or malformed returned mutation data can leave the outcome unconfirmed. Do not assert non-commit, automatic rollback, duplicate safety or password persistence from these files alone. Any misleading page copy is reviewed separately against its true source outcome.

## Decisions and next implementation contract

- Preserve URLs, existing grants, roles, RPCs and source-required password/reference checks. Unifying internal state names, adding capabilities or changing expiry/issuance validation is not a cosmetic migration.
- Class C candidates: preserve a valid non-secret id/issuance in existing recoverable redirects; truthful partial/unknown/identity/support copy using existing states; fail closed on contradictory validation data+error. Each candidate needs a defined scoped spec and independent review before its code change. Do not freeze all94 cases through such a bounded maintenance acceptance.
- Material gates: recipient status/reconciliation for unknown mutations, readiness-only retry, provider/SQL idempotency, authority revocation, actor/session races and concurrent metadata cleanup. Define amendments where guarantees change; never silently broaden service-role use.
- Data required for completion: versioned scenario mappings to source IDs; actor/tenant/issuance binding; original authoritative states; expected visible results, retained context and next action; applicable partitions including duplicate/stale/concurrent/unknown; actual exact-revision evidence. Outbound operations get their own map and are not omitted from full R2.
