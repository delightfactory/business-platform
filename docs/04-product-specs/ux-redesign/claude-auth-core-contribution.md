# R2-AUTH-CORE: مصفوفة السيناريوهات وتحسين الرحلة (مقترحة فقط)

**النطاق:** `auth/actions.ts`، `safe-next.ts`، `login/page.tsx`، `forgot-password/page.tsx`، `password/update/page.tsx`، `callback/route.ts`، `submit-button.tsx`، `lib/supabase/server.ts`، `proxy.ts`، `lib/supabase/proxy.ts`.

**خارج النطاق:** الدعوات والتفعيل وإدارة الشركة. لم أفحص أي قيمة سرية؛ ذكرت أسماء متغيرات البيئة فقط. كل ما يلي قراءة للمصدر، **ولم يُشغَّل أو يُختبر أي شيء**.

## 1. الأساس الحالي

### المهام والفاعلون

| البند | التفصيل |
|---|---|
| الفاعلون | زائر بلا جلسة؛ مستخدم يملك جلسة؛ مستخدم فتح رابط الاستعادة؛ نظام متصل بخدمة المصادقة (Supabase Auth) |
| المهام | الدخول؛ طلب الاستعادة؛ تعيين كلمة مرور جديدة؛ الخروج |
| تكرار المهمة | الدخول يومي؛ الاستعادة نادرة لكن كلفة الخطأ فيها عالية |

### الاعتماديات

- **متغيرات البيئة:** `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`server.ts:4-7`)، و`NEXT_PUBLIC_APP_URL`. الأخير شرطه https، أو localhost/127.0.0.1 (`actions.ts:30-34`، `route.ts:9-15`).
- **الخدمات:** خدمة المصادقة، وRPC `current_tenant_spaces` (`actions.ts:18`).
- **البروكسي:** `proxy.ts:9` يستثني `_next/static` و`_next/image` وfavicon والصور. باقي الطلبات يمر بـ`getClaims` وno-store (`lib/supabase/proxy.ts:14-28`).
- **كتابة الكوكيز:** `server.ts:18-22` يتجاهل فشل كتابة الكوكيز في مكونات الخادم، ويعتمد على البروكسي للتحديث.

### عناصر الواجهة الفعلية

**الدخول:**
- بريد: `type=email`، `required`، حد 254.
- كلمة مرور: `required`، و**`minLength=8`** (`login:37-39`).
- حقل `next` مخفي.
- زر «دخول» مع حالة انتظار «جارٍ الدخول…».
- رابط «نسيت كلمة المرور؟».
- شارة «بيئة التطوير» وتذييل «أساس التطوير» ثابتان في الكود (`:27,45`).

**طلب الاستعادة:**
- بريد وزر «إرسال رابط الاستعادة».
- رابط «العودة إلى تسجيل الدخول».

**تعيين كلمة المرور:**
- حقلان حدهما الأدنى 8، وزر «حفظ كلمة المرور».

**زر الإرسال** (`submit-button.tsx:11-15`):
- معطّل أثناء الإرسال ومعه `aria-busy`.
- يمنع النقر المزدوج أثناء الطلب، لكنه لا يحفظ أي قيمة بعده.

## 4. عيوب الرحلة المؤكدة من المصدر

1. **FP-06 وCB-03 وUP-06:** صفحة «منتهي» بلا نموذج، فهي طريق مسدود في ثلاثة مسارات.
2. **FP-05:** بعد «أُرسل» لا يمكن تصحيح البريد أو إعادة الطلب.
3. **UP-07:** فشل المزود يُعرض كخطأ تحقق. و**LI-07:** فشل الخدمة أو حد المعدل يُعرض كبيانات خاطئة.
4. **LI-04 وLI-06:** البريد يُفقد بعد التحويل. السبب أن النتيجة تمر عبر redirect وليس عبر حالة الفعل.
5. **CB-01 وCB-02:** 503 نص خام. **LI-05 وUP-05:** رسالة موجهة للمطوّر.
6. لا error/not-found في `/auth` (**LI-17**). الأخطاء تظهر كـ`status` لا `alert` (**LI-15**).
7. **LI-02:** فقدان الوجهة يتم بصمت (D8). **LI-10 إلى LI-13:** التحويل إلى `/operator` لا يميز السبب (D13).
8. **مخاطر تحتاج تحققًا وقت التشغيل:** LI-16 (الحد 8 عند الدخول)، وCB-04 (PKCE عبر جهاز آخر)، وCB-07 (اختلاف المضيف)، وSO-01 (نجاح خروج زائف).

## 5. التحسينات المقترحة (منفصلة عن الأساس)

**ثوابت لا تتغير في أي تعديل:**
- لا تخزين لكلمة المرور ولا إرفاقها كدليل.
- لا تغيير لمعنى الرد الموحد ولا لـ`safeAuthNext`.
- بقاء no-store.
- لا كشف لوجود الحساب.
