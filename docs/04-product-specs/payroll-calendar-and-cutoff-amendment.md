# Payroll Calendar and Cutoff Configuration Amendment

## Status

**Accepted planning amendment — Phase 0D HR Domain baseline, 2026-09-28.**

This amendment extends the Employee Finance & Payroll Specification with organization-specific payroll cycle configuration. It is not an Obal-specific exception. It is a required SaaS capability because organizations may define payroll periods differently from calendar months.

## Decision

Payroll Periods must not be modeled as fixed calendar months.

Each Employer Legal Entity within a Tenant must have one active effective-dated Payroll Calendar configuration that defines how its payroll periods are generated and closed. A simple one-Employer Tenant may receive a safe default during Payroll setup.

Example:

A company may define:

- Payroll cutoff day: 25
- Payroll period: 26th of previous month through 25th of current month
- Payroll run label: current payroll month/business period
- Payment date rule: configurable

For such an organization:

September payroll is not interpreted as:

`01 September → 30 September`

It is interpreted according to the Employer's Payroll Calendar:

`26 August → 25 September`

## Domain ownership

Payroll Calendar belongs to the Payroll domain, not Platform Core.

Platform owns:

- Tenant
- Legal Entity
- Sites
- Users
- Authorization

Payroll owns:

- Payroll Calendar
- Payroll Period generation
- Payroll cutoff rules
- Payroll close boundaries
- Payment cycle configuration

## Payroll Calendar model

A Payroll Calendar contains at minimum:

- Tenant
- Employer Legal Entity scope, with one active calendar per Employer at an instant
- Frequency (V1: monthly)
- Period boundary rule
- Cutoff day configuration
- Effective start date
- Effective end date when superseded
- Payment date rule
- Timezone context
- Active status

V1 supports a monthly cycle with configurable cutoff day.

Examples:

- Calendar month: cutoff day = last day of month
- Obal-style cycle: cutoff day = 25
- Other organizations: configurable cutoff according to their operational policy

## Effective dating and history

Payroll Calendar changes are effective-dated.

A cutoff change must not reinterpret historical payroll periods. The new rule applies only after the last generated period; any open run must be completed or explicitly cancelled before an affected future period is changed. The first period under the new cutoff begins the day after the preceding period ends, so the sequence has neither overlap nor gap.

Example:

Last period under the old calendar:

`01 Jan → 31 Jan`

Explicit short transition period:

`01 Feb → 25 Feb`

First ordinary period under the new 25th-day cutoff:

`26 Feb → 25 Mar`

The system preserves the old generated Payroll Periods exactly as they were created. The authorized Payroll operator reviews a transition period before approval. Its base pay is calculated for each covered local date from the effective monthly salary divided by 30 for `fixed_30_day`, or by the number of days in that date's calendar month for `calendar_days`; the dated amounts are summed and rounded under the existing Payroll rounding rule. The review shows the calculation and any explicit approved adjustment before lock. An earlier locked run is never changed silently.

A Payroll Calendar update affecting locked Payroll history requires a governed correction/amendment process, not silent regeneration.

## Integration with Attendance

Attendance does not calculate payroll directly.

However, approved Attendance inputs must map to the Payroll Period generated by the applicable Employer's Payroll Calendar.

Therefore:

Attendance review must answer:

- Which Payroll Period does this approved fact belong to?
- Is this fact included in the current payroll run?

The answer comes from Payroll Period boundaries, not calendar month assumptions.

## Integration with Payroll Run

Payroll Run generation uses:

`Employer-scoped Payroll Calendar`

then creates:

`Payroll Period`

then consumes:

`Approved Payroll Inputs`

then produces:

`Payroll Result`

The Payroll UI should present business language:

"Payroll September"

with the actual period dates visible when needed.

The user should not need to understand cutoff algorithms.

## UX requirements

Payroll setup must expose this configuration clearly to authorized administrators only.

Normal payroll operators should see:

- Current payroll period
- Start date
- End date
- Status
- Next action

They should not need to manually calculate date ranges.

The system should warn before changing a Payroll Calendar when:

- open Payroll Runs exist;
- Attendance inputs are pending;
- locked historical periods exist.

## Acceptance criteria

The implementation is complete only when:

- an organization can operate with a non-calendar payroll cycle;
- Obal's 25th cutoff scenario is supported without custom code;
- multiple tenants can have different Payroll Calendars;
- two Employers in one Tenant can use distinct active Calendars without mixing their periods;
- generated Payroll Periods preserve historical boundaries;
- a changed cutoff generates an explicit reviewed transition period with no gap or overlap, and cannot mutate an open run or locked period silently;
- transition-period pay and any approved adjustment are explained and reconciled before lock;
- Attendance inputs attach to Payroll Periods correctly;
- changing cutoff rules cannot silently alter locked Payroll history;
- mobile/desktop payroll workflows display the period clearly without exposing unnecessary technical complexity.

## Implementation constraint

Do not implement this as a customer-specific condition.

Do not create:

`if organization == Obal`

The capability must be part of the general SaaS Payroll configuration model.

## Accepted operational clarification — 2026-10-02

The [Cube 4 operational policy amendment](cube-4-operational-policy-amendment-2026-10-02.md) governs shorter-month cutoff, payment scheduling and prospective timezone behavior. Existing Employer scope, immutable history and contiguous transitions remain binding.
