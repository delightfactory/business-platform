# Payroll completion as one task

Authority: owner's 2026-10-16 request to make opening/creating, resolving blockers, reviewing, approving and recording payroll payment one direct safe journey. This accepts a focused interaction amendment; financial rules, permissions, source eligibility, history and request recovery remain authoritative.

Actor: company manager or delegated payroll stage owner. Entry: Payroll. Success: selected period's payroll finalized, external payment recorded and remaining amount visible. Split roles see the responsible next role. No bank transfer occurs in this product.

Independent design input: built-in payroll_journey_audit and official Claude Opus 5.5 Medium (session cc12b745-5440-418b-b9c3-277361bd2ec9). Both identify the absent-run entry into generic inputs, repeated selectors, parallel next actions and indirect issue repair as the core defects. Claude source review was bounded and did not execute runtime scenarios.

## Interaction contract

1. Payroll entry lists or opens saved periods and exposes the next-period preview/creation directly. First cycle uses the existing calendar contract; no unsupported arbitrary/disconnected dates. Never silently create a period or include excluded employees.
2. A run workspace calculates all eligible included employees using the existing command. Absent/cancelled: calculate. Stale: recalculate (or release approval first). Blocked: actionable blockers before details. Ready: approve. Approved and ready: finalize with explicit existing confirmation. Final: record external payment, or view statement according to actual permission.
3. One dominant action per state; no decorative linked stepper, duplicate source-resolution maps, or repeated selectors in the normal path. Advanced configuration, cancellation, correction and history remain discoverable.
4. A blocker opens the exact employee/task with explicit local return to the same period, never an unfiltered menu of input kinds. Reuse Egyptian setup and existing input validation/approval. Preserve entered values and existing opening balances. No generic external return URLs.
5. Employees have a compact review surface; source details/line breakdowns are expandable. Healthy employees remain discoverable with explicit filters and pagination.
6. Payment context retains employer, period and output; success distinguishes recording from actual transfer, shows paid/remaining and supports current recovery/correction.

Future attendance is not an input-setup defect. For monthly source coverage, show future/unreviewed dates and responsible source task; never fabricate attendance or allow daily manual units to bypass monthly source rules. General integration/qualification flags may follow one employee's incomplete coverage and must not be represented as three independently configurable company tasks.

## Acceptance

Run creation/refresh, representative direct blocker repair with return, approval/finalization and partial/full recorded payment use existing security and recovery boundaries. Exercise unknown-result journal before new financial actions; permission denial, stale state, empty scope, no/current/multiple periods, and future attendance remain honest. Check actual UI at 390/768/1366 widths and one relevant error/recovery. Record measured before/after only for journeys executed with the same actor/data/viewport; do not claim whole-module closure from source checks or synthetic screenshots.

Storage: external run worktree and outputs only; one writer, no new dependencies, no broad cache cleanup. Orchestrator retains concise reports/representative captures and owns stopping temporary processes and pruning obsolete intermediates. No main merge or paid service change; standing owner authorization covers development commits/push and qualified production release.
